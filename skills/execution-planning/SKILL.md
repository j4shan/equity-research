# Execution Planning

You are the **planner** in the main thread. Given a multi-step objective, you
produce a single **execution-plan document** that later governs how the work is
carried out — the DAG decides *when* each task runs; the caller's own knowledge
decides *how*.

This skill is general-purpose. It is invoked directly by a user, or as the first
step of another skill (e.g. `equity-research`) that then executes the plan.

## Inputs

The caller supplies (as arguments or inline):
- **objective** — the goal to plan for (one line is fine).
- **output** — the path to write the plan to. If a caller passes one (e.g.
  `RUN_DIR/plan.md`), use it verbatim; otherwise default to `./execution-plan.md`.
- **subagents** *(optional)* — the subagent types available for delegation. If
  none are given, plan every task on the main thread.

## Procedure

### 1. Decompose
Break the objective into **5–15 discrete tasks**. Give each a stable
kebab-case id and a one-line success criterion (what "done" means). Prefer tasks
that are independently checkable and, where possible, independently runnable.

### 2. Declare dependencies and sort
Express the graph as `{task_id: [prerequisite_ids]}` (tasks with no prerequisites
map to `[]`) and call **`mcp__research_hub__plan_toposort(dependencies)`**.
- Never compute the order or the waves yourself — this tool is the single source
  of truth for both.
- If it returns `{"error": "cycle detected: ..."}`, your decomposition has a
  circular dependency. Fix the graph and call again. Repeat until it succeeds.
- The tool returns `order`, `waves` (parallel batches), `roots`, and counts.

### 3. Assign executors
For each task decide **main-thread** vs **subagent:<type>**:
- I/O-heavy, independent analysis that maps to an available subagent → delegate.
- Anything needing global/shared state, cross-task synthesis, or invoking the
  `Skill`/`Task` tools → keep on the main thread (subagents cannot reliably spawn
  further subagents).
- With no subagents available, everything is `main-thread`.

### 4. Write the plan document
Write to **output** with exactly these four sections (this structure is the
contract callers rely on — keep the headings verbatim):

- `## Objective Tracker` — a checkbox table. Columns:
  `| # | Task | Success criterion | Status |`. Status ∈
  `pending | in_progress | done | failed`; start every row at `pending`.
- `## Task DAG` — (a) the exact `plan_toposort` input as a fenced ```json block,
  then (b) the **Waves** table straight from the tool output:
  `| Wave | Tasks (parallel) | Depends on |`. Note that this table is
  machine-generated by `plan_toposort` and is authoritative for ordering.
- `## Task Assignment` — `| Task | Wave | Executor | Rationale |`, where Executor
  is `main-thread` or `subagent:<type>`.
- `## Execution Protocol` — dispatch **wave by wave**: within a wave, launch all
  `subagent:` tasks in a **single message with multiple `Task` calls** (true
  parallelism) and perform `main-thread` tasks yourself; update the Objective
  Tracker as each task finishes; a wave begins only once the previous wave's
  tasks are `done` (or explicitly waived with a noted reason).

See `examples/sample-plan.md` for a fully worked plan.

### 5. Mirror and report
Mirror the tasks into `TodoWrite` so progress is visible in-session, then report
the plan's path back to the caller so execution can begin.

## Notes
- The plan is a living document: whoever executes it updates the Objective
  Tracker statuses in place.
- Re-planning mid-run is fine — re-run `plan_toposort` with the revised graph and
  rewrite the affected sections; never edit the Waves table by hand.
